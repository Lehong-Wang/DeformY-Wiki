# Build-vs-Reuse Brainstorm

## Recommended reuse stacks, must-build components, deep reads, red flags

**Framework-coherence call up front.** Keep the learning core in **PyTorch**. Treat CNP-B (TensorFlow/TF-Graphics) and LAPA (JAX) as *read-only recipes*, never dependencies — build the learned pieces on the MMP++/QueST/ProDMP (mp_pytorch) side. Mixing TF-Graphics manifold code into a Torch GPU-sim loop is not worth the integration tax for a first milestone.

**Two framing insights that drive everything.**
1. **Step 0 needs no learned decoder.** A fixed ProDMP/parametric-curve basis *is* a compact action decoder (params → smooth joint trajectory); CMA-ES searches those params directly against the batched sim. Learned manifolds (MMP++/QueST) only earn their keep at Step 1, when you compress the oracle's own solution set into a low-dim, target-conditioned latent. Don't front-load a VAE you can't yet supervise.
2. **Flying Knots is the north-star for every stack** — same problem family (single feedforward rope trajectory, no feedback, few-shot cross-rope transfer, real xArm7 + Vicon, Drake+Elastica+PyTorch, MIT). Read it end-to-end before writing any glue. It is a reuse candidate for the *evaluation + real-arm loop and the critical-point objective*, not the learning core.

### Recommended reuse stacks

**STACK A — "MP-native episodic RL" (build this now; Step 0 → Step 1, fastest, most maintained).**
Thesis: ProDMP is your compact action space from day one; the CMA-ES oracle amortizes into episodic RL that reuses the *same* parameterization, so Step 0 and Step 1 share code.
- **Compact decoder (Step 0):** the `mp_pytorch`/ProDMP backbone from **Movement Primitive Diffusion** (MIT) — use only the MP layer, not the diffusion head.
- **CMA-ES oracle (Step 0):** `pycma` with **Diffusion-ES**'s gradient-free ES loop as the pattern (strip the diffusion + AV plumbing, keep mutate→score-by-sim-rollout).
- **Batched feasibility map (Step 0):** *we build this* — vectorized rollout of N ProDMP samples through the GPU sim → tip trajectory → (position error, arrival-direction error, joint-limit violation) tensor. Core new code; no repo owns your sim's API.
- **Goal-conditioned zero-shot training (Step 1):** **TOP-ERL** (shares ProDMP with the decoder), **TCE** (GPL-3.0) as fallback. Both do off-policy episodic RL over MP params — "reward only at completion, no per-step feedback."
- First-week deliverable: the batched-sim feasibility harness + `pycma` over ProDMP — that alone tests whether a single open-loop swing can even hit target+direction in sim.
- Main risk: ProDMP is a *fixed* basis — may not compactly express wind-up-then-throw (sharp release velocity peak). Mitigate: more basis functions or an explicit release-phase segment.

**STACK B — "Learned latent manifold + gradient-free latent planning" (the later decoder milestone).**
Thesis: run Stack A's oracle to *generate* optimal trajectories, then distill them into a low-dim target-pose-conditioned manifold — CNP-B's "offline-optimal → supervised-manifold → fast-inference" recipe, done in PyTorch.
- **Decoder:** **MMP++** (primary; latent of parametric curves, task-conditionable, via-point modulation, SE(3)) or **QueST** (VQ tokens + GPT, if the swing is better as discrete wind-up/throw tokens).
- **Oracle → dataset:** Stack A's CMA-ES + your sim produce (target pose → optimal trajectory) pairs.
- **Test-time planner:** **Diffusion-ES** ES loop over the *latent*, scored by sim/forward-model rollout — robust planning without differentiating rope physics.
- **Equivariance (later):** **EMMP** — exploit SO(2) symmetry about the arm base to generalize across a *ring* of target directions from sparse data (same MMP lineage → cheap swap-in).
- Main risk: two-stage cost, and latent ES can wander to "valid latent, infeasible trajectory." Mitigate: keep the batched-sim feasibility harness as a **hard filter on every latent sample**.

**STACK C — "Physics-conditioned forward model + calibration" (the per-rope / RMA milestone).**
Thesis: "few-minute per-rope calibration, zero per-target adaptation" is a system-ID problem — build an in-context forward model so calibration = feeding a short rollout as context, no explicit refit.
- **Forward model (action → whole tip trajectory):** **RoboMorph** (in-context meta-dynamics Transformer; feed calibration rollout as context tokens) or **IIDA** (implicit-context vector if a rope isn't captured by a small parameter set).
- **Calibration exploration:** **ASID** — Fisher-information-maximizing exploration is exactly the short diagnostic swing before committing.
- **Robust parameter distribution:** **DROPO** — a *distribution* over rope params → score candidate swings on worst-case/expectation (pessimistic planning).
- **In-context specialization recipe:** **sysid-transformers-transfer** — benchmarked "extend the context window vs. lightly fine-tune?" for a new rope.
- **Real-arm + eval harness:** **Flying Knots**.
- Main risk: forward-model accuracy at the high-dynamics release instant — small error amplifies through the whip into large tip-position error at impact. Mitigate: use the forward model only to *shortlist*, then verify shortlisted swings on the actual GPU sim before real execution.

**Opinionated sequencing.** Build Stack A now → graduate to Stack B once the oracle has enough solutions to distill → fold Stack C's calibration pieces (ASID + RoboMorph/IIDA + DROPO, decided by sysid-transformers-transfer) into the *same* manifold by conditioning it on the in-context/physics vector, not as a separate system.

### Must-build components (no reusable code — this is the real work)

- **The objective itself: tip → 3D position arriving along a 3D DIRECTION on a deformable tip.** Nothing implements this. Flying Knots targets tip-*position* only; air-hockey does velocity-vector hitting but 2D/rigid-puck. **Cleanest path: extend Flying Knots' critical-point QP objective with a velocity-direction residual.**
- **The GPU-parallel rope-targeting ENV + reward.** SoftMimicGen ships the only public GPU rope-whip *scene* (asset reusable), but the targeting-task wrapper, tip-state → whole-trajectory-tensor extraction, arrival-direction reward, and vectorized many-target eval harness are all build-it-yourself.
- **Limit-cycle / energy-pumping wind-up primitive.** True whitespace — zero code anywhere covers periodic-orbit energy accumulation before a throw. (Creative angle: use PRISE/QueST tokenization to make the *wind-up count* a searchable discrete variable — a repeated wind-up token + a release token; PRISE's BPE handles variable duration better than QueST's fixed grouping.)
- **Deformable-specific in-context calibration → whole-trajectory forward model.** RoboMorph/IIDA architectures transfer, but the deformable data pipeline and the "context = few-minute calibration swing" framing don't exist — you build the adaptation.
- **The end-to-end integrated system.** No repo maps `target pose → single open-loop joint trajectory` via latent search over a rope-tip manifold with a per-rope context. D-Cubed is the closest published match and has no code. The glue is yours.

*High-leverage recombinations to consider:* (1) sim-trained manifold decoder as the ILC *prior* inside Flying Knots — sim gives the open-loop prior for any target, Flying Knots' QP-ILC does the few-shot real-arm correction (reuses a working real-arm codebase as the sim-to-real closer). (2) ES/CEM search *inside* EMMP's equivariant manifold — collapses the search space by the symmetry group. (3) ASID's info-maximizing exploration feeding an *implicit* (IIDA/RoboMorph) context vector instead of ASID's explicit fit — exactly "few-minute calibration → no explicit rope params."

### Top-3 deep-read repos

1. **flying_knots_public** (MIT, RSS 2026) — *highest priority; same problem family, real arm, working end-to-end.* Read: (a) the critical-point/"decisive instant" QP feedforward-update objective — your direct template, key question **how to add a velocity-direction residual**; (b) the loose point-mass rope model (how crude can the model be and still transfer?); (c) the per-rope identification procedure (how few trials, what's fit); (d) feedforward trajectory parameterization.
2. **CNP-B** (T-RO 2024, TensorFlow) — read for how the net ingests a constraint set + start/goal and emits a full on-manifold trajectory in one pass; the offline-optimal → supervised-manifold recipe; whether *arrival direction* is expressible as a constraint; and inference cost (needs to be cheap enough for a latent-search inner loop). **Extract the recipe, port to PyTorch — do not vendor.**
3. **SoftMimicGen** (Apache-2.0, Isaac Lab) — read for the rope asset/scene definition, dynamic rope-whip task setup, tip-state extraction, and env parallelization: the training-env skeleton you'll graft the targeting reward onto. Confirm Isaac Lab/Sim version and how tightly rope physics couples to it.

### Red flags

- **License = unknown/unspecified → legally NOT reusable by default (read for method, don't vendor until confirmed):** TOP-ERL (none), Diffusion-ES, streaming-flow-policy (none), MMP++, ATACOM/rl_on_manifold, IIDA, ASID, AdaFlow. **TCE is GPL-3.0** — usable but copyleft; note the implications.
- **Anonymized / ephemeral:** TOP-ERL lives under `toperliclr2025` (anonymous review handle, ★9, no license). Confirm it still resolves and find the authors' canonical de-anonymized repo before building on it.
- **Isaac Sim/Lab version lock-in (brittle across releases):** SoftMimicGen and PACE both pin specific versions (PACE: Isaac Sim 4.5.0 / Isaac Lab 2.1.0 + RSL_RL + LeggedLab). Budget setup pain; pin your toolchain. PACE is additionally humanoid-specific — the *pattern* transfers, the code doesn't.
- **Archived / dataset-only:** competitive_robot_table_tennis is archived, ships dataset + viz only, rigid-paddle closed-loop — eval-protocol inspiration at best.
- **Aging / dead-dependency stacks:** IIDA (mjrl/mujoco-py unmaintained), ATACOM/rl_on_manifold (last real activity 2021-11), DROPO/AdaptSim (2022-23; AdaptSim is Drake-heavy). Work as references; expect environment-setup friction.
- **Dependency baggage to strip:** Diffusion-ES is built on nuplan-devkit + tuplan_garage (AV stack) — significant plumbing to remove before the ES core is usable.
